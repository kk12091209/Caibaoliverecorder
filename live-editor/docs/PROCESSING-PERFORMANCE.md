# 本地处理性能验证（2026-10-23）

本轮仅在本地实现和验证，没有推送或发布。对照基线是本轮开始时的工作区快照，包含此前尚未发布的调度、缓存和索引优化，**不是 Git HEAD 或线上 v0.2.7**。

## 保留的改动

- 闲时处理先测单块吞吐，再在 CPU、内存、磁盘和缓存预算允许时试双块。同素材的双块单位处理耗时至少下降 10% 才继续；连续两轮收益不足退回单块。编码参数、帧率、分辨率、字体和弹幕数量不变。
- 开始录制和前台操作时沿用后台让出机制。失败先取消并等待同批任务退出，再以相同编码配置仅重试未完成块；保留已验证的缓存，释放所有空间预留及读取租约。
- 补充后台阶段计时、策略原因与可复现的隔离基准脚本。
- 修复多段音频在短尾、静音与有声段混拼时可能截短的问题：多段 FLAC 统一 s32 样本格式及 800 样本块，最终转换遇到解码错误立即失败。单段仍保留原 FLAC → AAC 路径。

没有保留“单段直接编码 AAC”的候选优化。它减少一个中间文件和进程，但 300 秒正弦样本独立 ABBA 复测中，旧链约 3.10 / 3.90 秒，候选约 5.15 / 7.58 秒。进一步保持整数混音语义也未消除该类素材的回退；60 秒复杂音频局部收益不足以证明通用优势。本轮不宣称音频导出提速。

## 方法和边界

- 机器：Apple M5，10 核、16 GiB；Node 24.12.0；FFmpeg 9.0.2。
- 同一份 300 秒 `testsrc2` 动态图案，1920×1080、30 fps、H.264 FLV、48 kHz AAC 正弦音频，原片约 656 MiB。生成与导入不计入媒体处理耗时。
- 输出 1920×1080、60 fps，固定中文字体，每秒 3 条弹幕，60 秒一块。视频帧数、音画时长及分块附近画面均校验；性能计时不包括校验。
- 每种编码方式按旧→新→新→旧运行，各版本两次，串行测试，未主动清空系统文件缓存。测试数据库、素材副本和输出均位于隔离临时目录，不打开用户数据库。
- 两小时数字按 `本次阶段耗时 / 实际素材秒数 × 7200` 线性外推，**并非实际录制或处理两小时素材的实测**。真实内容复杂度、散热、机器负载及缓存容量会改变结果。
- 本轮不改变正在录制时暂缓后台工作的策略。因此“录制两小时”不等于“后台有两小时可用于预处理”。下列准备耗时是录像具备处理条件后的工作量，不是录制时长，也不是准备完成后点击导出的等待。
- 未在 Windows 或 NVIDIA / Intel / AMD 硬件上跑性能对照，不能把本机结果当作这些设备的承诺。

## CPU 后台准备

| 次序 | 版本 | 5 分钟素材处理耗时 | 两小时线性估算 |
| --- | --- | ---: | ---: |
| 1 | 优化前 | 137.09 秒 | 54.8 分钟 |
| 2 | 优化后 | 91.91 秒 | 36.8 分钟 |
| 3 | 优化后 | 79.15 秒 | 31.7 分钟 |
| 4 | 优化前 | 90.82 秒 | 36.3 分钟 |

两次结果的中位数：113.96 → 85.53 秒，**本轮观察到耗时下降 24.94%**；两小时对应约 45.6 → 34.2 分钟，少约 11.4 分钟。

每版仅两次，这里的中位数也是两值平均；旧版两次相差约 51%，新旧范围存在重叠，不能将全部差异都归因于代码，不能承诺普遍稳定快 25%。两轮新版内部的双块单位素材处理耗时分别比本轮串行采样低约 35% / 26%，说明并行策略确实获得了吞吐收益。

CPU 测量使用的早期候选与最终版本只在 `audio()` 有差异；后台准备不调用该路径，因此本节准备阶段数据仍适用。早期候选的整片导出和短剪辑耗时经过已撤回音频路径，**从最终性能结论中剔除**。CPU 组没有可用 RSS 采样，不报告内存变化。

## Apple 硬件编码：最终版本

四轮均实际使用 `h264_videotoolbox`，没有软件回退。旧版准备耗时 67.21 / 66.49 秒，新版 67.13 / 67.17 秒；双块没有达到 10% 收益门槛，两轮均自动回到单块。

| 阶段 | 旧版中位数 | 最终版中位数 | 两小时粗估：旧 → 新 |
| --- | ---: | ---: | ---: |
| 后台准备 | 66.85 秒 | 67.15 秒 | 26.74 → 26.86 分钟 |
| 准备完成后的整片导出 | 4.57 秒 | 4.69 秒 | 1.83 → 1.88 分钟 |
| 未对齐缓存边界的 30 秒剪辑 | 7.07 秒 | 7.16 秒 | 不外推 |

这一组没有可确认的提速，准备耗时相差约 0.45%，导出相差约 0.12 秒。不能宣称所有机器都会变快；保持现有硬件编码路径和自动回退，比强制并发更合适。两小时素材若尚未准备，从准备到整片导出按阶段粗估约 28.6 → 28.7 分钟；若已在闲时准备好，只需看导出行，不能把两段等待重复计算。

硬件组新旧 16 处缩小灰度帧采样完全一致（含分块附近）；每次整片输出均为 18001 帧，30 秒剪辑为 1800 帧，音画时长均通过检查。这是抽样画面对照与帧表/边界解码验证，不等于逐帧像素全量比对。

硬件组采样包含基准 Node worker 和当时活动的媒体子进程，后台准备峰值约 400～465 MiB；它不包含操作系统全部开销和 GPU 内存，也不是完整桌面应用峰值。没有据此宣称内存减少。

## 回归结果

- 录包机完整测试：746 项，742 通过、0 失败、4 跳过，约 83.5 秒。跳过的是两个 Windows 专属测试及两个需显式启用的真实录制核心冒烟测试；本轮没有把合成素材验证当成真实直播录制验证。
- 新增策略 9 项、资源生命周期集成 6 项、真实 FFmpeg 音频完整性 8 项，均包含在上述完整测试中。集成测试连接真实调度器、缓存及后台状态机，通过可控子进程覆盖双块取消、录制让出、关闭、重试及空间不足；音频测试覆盖延迟起音、缺包空档、静音混拼、短尾、30/60 fps 和损坏解码。
- `npm run build` 成功；`git diff --check` 通过。
- 测试结束后核对，当前 `server/`、`shared/` 与最终基准快照 SHA-256 一致。未修改前端样式，未增加第三方运行时依赖。

## 复现与原始证据

本地证据目录：`/private/tmp/caibao-speed-20261023/`。

- `baseline-state.json`：基线 HEAD 与开始时的未提交文件清单。
- `before/`、`after/`、`after-accepted/`：旧版、早期候选、最终版本源码快照；`code-hashes.json` 保存 SHA-256。
- `cpu-summary/report.json`：CPU 四轮原始阶段计时和画面比较（最终只采用其中 preparation）。
- `gpu-summary/report.json`：最终版本与基线的硬件编码四轮对照，包括音画、帧数、边界采样和进程资源记录。
- `audio-abba.json`、`audio-s32-abba.json`、`audio-s32-complex-abba.json`：未保留音频方案的探索结果。
- `full-tests.log`：完整测试输出。

从项目根目录执行（运行时路径按本机实际位置替换）：

```sh
TMPDIR=/private/tmp .tools/runtime/node-v24.12.0-darwin-arm64/bin/node \
  live-editor/scripts/benchmark-processing.mjs \
  --base /private/tmp/caibao-speed-20261023/before \
  --after /private/tmp/caibao-speed-20261023/after-accepted \
  --source /private/tmp/caibao-speed-20261023/source-1080p.flv \
  --duration 300 --size 1920x1080 --repeats 2 \
  --acceleration software --scenarios warm,clip \
  --output /private/tmp/caibao-processing-new-report
```

`auto` 会尝试本机硬件编码，必须检查报告中的实际 encoder，不能把软件回退算作硬件结果。输出目录须为新目录；基准会复制输入文件后再写弹幕副本。`--full-validate` 可启用逐帧解码计数；默认采用 MP4 帧表计数和边界解码。未传 `--source` 时可自行生成素材，但生成配置含 B 帧，与本轮重用源不同，不能直接混合统计。
