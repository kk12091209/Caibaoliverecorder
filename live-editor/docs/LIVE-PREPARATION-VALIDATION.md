# 录中提前处理：本地实现与验证（2026-10-23）

本轮仅修改本地开发版本，未提交、推送或部署。目标是在不改变画质、帧率、弹幕规则的前提下，把一部分处理移到录制期间，减少停录后的等待。编码本身的速度与停录后等待分别衡量。

## 使用与范围

设置中的“录制时自动提前处理”默认关闭，需同时启用自动预处理总开关。首版仅对单路、接电、可确认系统资源与硬件编码健康的 Mac 准入。Windows、缺少监测信息的设备、电池模式、多路录制和 CPU 编码继续沿用录后处理。录中功能不自动导出成片，也不影响手动剪辑和弹幕设置。

继续采用 60 秒缓存块、现有编码参数与帧率，保留约 90 秒尾部；原片写入与预处理任务独立。视频、XML 与连麦索引必须具备条件；混合编码头的来源暂缓录中处理。录制、录后整理以及最终导出使用同一区间身份，追加和经过验证的原片整理不会让旧缓存无故失效。

迟到弹幕、防重复回撤、昵称/头像和样式变化仍重新核对完整布局。只对证明有效的块复用，不以省略弹幕或降低质量换取速度。

## 资源和故障退让

- 全局最多一个录中预处理任务；以每 60 秒约 18 秒实际处理时间为初始预算。它不是 CPU 使用率限制。
- 首次约 30 秒健康观察。接电、热状态、可用内存以及实际字节和媒体时间推进共同决定准入。
- 检查写盘耗时、索引积压和事件循环延迟。普通预算不足不重算当前块；严重异常取消后台任务，等待进程退出，再按 60/120/300 秒冷却，同场反复异常停用提前处理。
- 等待下一个完整块时按素材时间停止重复媒体探测，健康检查继续。录制结束后不继承录中等待，交回原有闲时处理补尾段。
- 新增只读 macOS 资源助手，本机构建约 59 KB，无新增第三方运行时依赖；采样约每 10 秒一次，不在录制期间编译。

完整布局仍包含同步排序和对象复制。隔离元数据压力测试中，2 小时、每秒 50 条的 36 万条弹幕重建约 3.6～3.8 秒，单次事件循环延迟约 473～498 ms。因此在进入录中布局前加有界计数：超过 5 万条弹幕或 1 万个连麦布局记录就暂缓录中处理。数据全部保留，录后使用完整路径。该门槛是保守保护，不是所有机器均无感的承诺。

对照元数据测试：2 小时、每秒 3 条约 94～114 ms，最大事件循环延迟约 33～35 ms；每秒 10 条约 308～424 ms，最大延迟约 92～102 ms。这里只衡量布局，不代表整片渲染速度。

## 本机对照结果

Apple M5、10 核、16 GiB，实际使用 `h264_videotoolbox`，两组编码参数相同。下表是同一份 5 分钟素材的单次关闭／开启对照，包含停止后的索引收尾、原片整理、剩余预处理、音频和封装。

| 项目 | 关闭录中处理 | 开启录中处理 |
| --- | ---: | ---: |
| 录制写入耗时 | 300.02 秒 | 300.02 秒 |
| 停录后到完整弹幕成片 | 73.88 秒 | 34.70 秒 |
| 停录前已完成的视频 | 0 秒 | 180 秒 |
| 录中写入调度延迟 p95 | 2.25 ms | 2.04 ms |
| 录中写盘耗时 p95 | 1.20 ms | 0.92 ms |
| 录中索引落后 p95 | 1,212 ms | 1,303 ms |
| 录中事件循环延迟 p99 / 最大值 | 22.72 / 28.77 ms | 22.74 / 62.13 ms |
| 录中采样内存峰值（Node＋媒体子进程） | 197.98 MiB | 425.89 MiB |

本次停录等待减少 **53.03%**，提前处理的 3 个完整块在封口、原片整理后均被最终导出实际复用。原始 FLV 的 SHA-256 一致；两组成片均为 1920×1080、60 fps、18,001 帧，音画时长均约 300.017 秒；10 处边界附近的缩小画面样本完全一致。

录中成功块分别用时约 13.18、13.31、13.48 秒。另外一次首块处理在发布前未通过元数据复核，返回等待并重新处理；这次约 13.07 秒的工作没有发布为可复用缓存。**录中实际工作合计约 53.03 秒，有效块工作约 39.96 秒**，全部计入资源预算和真实计时，不能仅用成功块耗时推算可持续速度。该次重算体现了先保证内容一致再复用的取舍。

录制期间媒体子进程最多 1 个。样本内存峰值增加约 228 MiB，事件循环最大值有所增加；没有观察到原片字节丢失、录制错误或明显的 p95 写入延迟恶化。这是有限条件下的一次验证，不代表所有设备无感，也不是网络漏录概率的统计。

同样复杂度下的 **2 小时模型估算**：全部停录后处理约 **29.6 分钟**；若录中始终满足准入、30% 工作预算可用且缓存持续有效，预计停录后约 **2.4 分钟**。估算包含本次未发布工作的损耗；按净吞吐计算，持续跟上录制的余量并不宽裕，因此前台抢占、长时散热或更密集弹幕会增加剩余工作。该数字不是两小时实测，也不表示编码器本身提速十几倍；收益主要来自把工作前移到录制期间。

## 回归与页面验证

- 最终完整测试 816 项：812 通过、0 失败、4 跳过，约 30.8 秒。跳过的是两个 Windows 专属项目、两个需显式启用的真实录制核心冒烟项目。
- 验证封口范围身份、原片整理后复用、关键帧和文件篡改、历史编码头、迟到弹幕与连麦变化、暂停/关闭后的子进程和租约清理、预算与冷却、实际录制健康及设置校验。
- 高密度保护另验证：达到门槛后不启动媒体探测或布局排序，不删除数据，录后仍进入完整布局路径。
- Vite 构建通过；Chrome 桌面 1440×1000 和窄屏 390×844 验证默认关闭、保存与刷新持久化、总开关联动、失败回退、进度和退让提示，未发现相关控制台错误。真实本机 API 使用隔离空目录验证，没有读取现有录像。
- 最初一轮媒体测试命令漏设 Mac 工具路径，旧默认路径指向 Windows `ffmpeg.exe`；纠正测试环境后完整重跑通过，未为此修改业务逻辑。

## 媒体对照方法与限制

同一份约 300 秒的动态 `testsrc2` 视频，1920×1080、30 fps、H.264 FLV 与 48 kHz AAC 音频，每秒 3 条中文弹幕。两组均按 1 倍时间以完整 FLV 标签写入，使用真实 Ingestor、连麦索引、预处理调度、资源策略及 VideoToolbox 编码；最终输出保持 1920×1080、60 fps。顺序为关闭 → 开启，各一次，没有与其他媒体回归任务同时运行。

资源采样来自本机真实电源、温度与内存；录制健康输入来自隔离回放写入器。不是 B 站或抖音网络直播，也没有在本轮吞吐实验中注入真实断网。原片 SHA-256、输出帧数/音画时长、分块附近画面解码和缓存实际复用分别检查。画面抽样不能代替全量逐帧像素比较。

停录等待包含最终索引、经过验证的原片整理、剩余预处理和最终音频/封装。采样 RSS 仅包含基准 Node worker 与活动媒体子进程，不包含整套桌面应用、GPU 分配和全部系统缓存。资源使用并非零成本。

关闭组首次输出验证遇到基准脚本参数 `.2` 不被 FFmpeg 接受；改为 `0.2` 后验证同一成片，保留原始阶段计时，没有改动产品代码或重新选择更快的一轮。

两小时数字使用短样本吞吐、30% 工作时间预算、90 秒尾部和 60 秒分块建立模型，不是两小时实录。只有持续单路接电、资源健康、无前台抢占、弹幕规模在门槛内且缓存有效时才适用；热压力、画面/弹幕复杂度、磁盘和前台操作都会使收益下降。
