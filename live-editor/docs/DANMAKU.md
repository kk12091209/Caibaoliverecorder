# 弹幕保存与洪峰处理

B 站和抖音使用独立的平台接入，最终都写入原片旁的 XML，再通过现有索引、浏览器预览、弹幕排除、密度、预处理和导出流程处理。

每个正在录制的房间默认最多索引 **50 条/秒**，可在设置中拖动调整为 **1～50 条/秒**，自动保存，额度按直播间独立计算。十个房间正常采集时合计可保存 500 条/秒；仅监控、未录制的房间不占弹幕保存额度。这个数字是默认策略，不是经过真实十万人直播间验证的性能上限。

处理顺序：

1. 只保存普通聊天，礼物、点赞、进场、关注和系统提示忽略。抖音先按聊天本身的福袋参与标记过滤，再用明确活动口令与有效时间补充过滤；B 站按明确的抽奖活动过滤。30 字及以上的普通弹幕不索引；抖音采集在写 XML 前同时舍弃长消息。字符按 Unicode 码点计算，汉字和 emoji 不会按 UTF-16 的两个半字计数。表情包占位沿用现有规则。
2. 对剩余弹幕按接收秒进行蓄水池抽样，超额时随机保留该秒内设置额度的条数，不只保留最先到达的消息。
3. 每个录制房间最多积压 2,000 条、8 MiB 估算负载；每个采集进程的房间共享 32 MiB 上限，B 站核心和抖音工作线程各自执行此限制。单条负载超过 16 KiB 时舍弃。正在写入的批次也计入额度，磁盘受阻时停止扩大积压。额度约束保留负载，不等于整个进程的内存上限。
4. 每个正在采集的房间只运行一个异步写入循环，不为每条弹幕创建 `Task.Run`。最多约一秒后写入已结束的时间桶，保留接收时的位置；停止或切换原片时收尾当前桶，旧片段的消息不能流入新原片。

抖音原始 XML 只保存抽样后的弹幕，同时每秒写一条 `density` 汇总：`ts` 是原片相对秒，`count` 是过滤后、抽样前的普通弹幕数，`kept` 是实际保留数。数据库的 `danmaku_density` 仅保存省略数量 `count - kept`，密度图叠加这些计数与已保存弹幕，避免峰值被配额压平。手动排除某条已保存弹幕时，其密度仍减一。旧素材没有汇总时继续按已保存弹幕计算。

删除素材时汇总随 source/session 一起删除；导出成片和任务记录仍按原有保护规则保留。没有额外弹幕副本或纯净视频缓存。

实现位于录制核心的 `Danmaku/BoundedDanmakuBuffer.cs`、`BasicDanmakuWriter.cs`，抖音的 `server/douyin-*.js`、`chat-intake.js`、`lottery-activities.js`，以及工作台的 `server/ingest.js`、`server/density.js`。B 站视频下载、导出编码参数、预处理让路及缓存上限保持原有行为。

## 抖音接入

粘贴 `https://live.douyin.com/<webRid>` 后自动识别平台，通过临时匿名访客信息获取房间状态和直播流；不要求用户登录、填写 Cookie 或签名服务。完整链接移除跟踪参数，短链接每次跳转均验证平台域名；无法确认房间时提示改用完整链接，不尝试任意外部地址。

优先选择平台返回的最高 H.264/AAC FLV，包括可用的原画，跳过明确的 HEVC/AV1、纯音频地址。直播 CDN 地址及跳转有域名白名单，部分原画地址使用平台返回的 HTTP；访客 Cookie 不发送给视频 CDN。仅规范化 FLV 解码时间戳，压缩图像和音频负载保持原样。具体分辨率、帧率及权限由直播间提供。

一个共享工作线程完成 WebSocket、protobuf、gzip 解码和抽样，不阻塞编辑器的 SQLite 线程。最多 64 个抖音监控/采集房间；每房间最多一个未确认的写入批次，父线程完成 XML 写入后才释放额度。帧上限 8 MiB、解压上限 16 MiB，每包最多保留 20,000 个聊天载荷及 256 个活动/控制载荷；礼物等载荷不展开解析。单条异常聊天跳过，连接异常自动重连，视频继续录制。采集线程按短期消息 ID 去掉网络重发；同文重复规则由共用索引处理。

福袋过滤优先读取 `WebcastChatMessage` 的 `chat_by`（protobuf 字段 20）：值为 9 或 10 时按抖音网页自己的福袋弹幕识别规则丢弃，在解析用户信息、抽样和密度汇总前执行。不依赖加入房间之前的活动通知，也不要求文字含有“福袋”。`chat_tags`（19）和优先级（21）不参与此判断，普通聊天交给下述共用长度与重复规则处理。规则参考 [抖音网页弹幕设置模块](https://lf-webcast-platform.bytetos.com/obj/webcast-platform-cdn/webcast/douyin_live/chunks/DanmaSetting.eddd4c0c.js)，字段参考 [协议定义](https://github.com/jwwsjlm/douyinlive-proto/blob/main/protobuf/new_douyin.proto)。

活动口令作为补充：当前 `WebcastLotteryEventNewMessage` 按 Common 的房间编号、活动编号、起止时间和 `conditions_detail`（21）的评论类型 3 读取；旧 `LotteryInfo` 的 `conditions`（8）也读取明确评论类型，缺少类型时才检查说明文字。结束消息关闭对应活动。同包活动先于聊天处理，尚未写出的当前桶再次核对活动。缺失或过期活动不推断口令，不按重复次数猜测删除。

真实房间 `974612852909` 的匿名读取捕获 9 条聊天，其中 7 条带 `chat_by=9` 的参与评论全部过滤，2 条普通聊天保留；活动查询当时没有返回口令。脱敏 protobuf 样本保存在测试夹具中，去掉用户资料和消息标识；另有 9/10 类型、普通同文、活动条件、洪峰和密度测试。旧版已保存的 XML 没有 `chat_by`，无法对所有历史参与评论精确追溯；不会凭重复文字将旧弹幕判定为福袋；独立的同文去重规则仍适用。

访客 Cookie、CDN 签名和弹幕签名只在内存使用，不持久化账号信息，不暴露给页面快照或日志。HTTP/WS 签名使用本地互操作实现，不加载浏览器 SDK 或远程签名服务。来源与许可见 [第三方声明](../../THIRD_PARTY_NOTICES.md)；协议参考 [dy-comment-cast 的 protobuf 定义](https://github.com/adseng/dy-comment-cast/blob/master/proto/douyin.proto)和公开 Web SDK 的 LotteryInfo 字段。平台接口变化、访客权限和风控可能影响特定房间，错误不作为“已下播”处理。

删除素材时 XML、原片、小段、render-cache 和平台会话元数据随素材清理；导出成片和任务记录仍按现有规则保留。没有额外弹幕副本或纯净视频缓存。录完只自动预处理，成片继续手动导出。

## 共用显示规则

列表、预览、密度和新导出使用相同规则：同一素材、相同文字在滚动 10 秒内达到 5 条时保留一条，前面已索引的重复项也标记隐藏。不足 5 条的重复聊天保留；持续刷屏每 10 秒最多显示一次。活动过滤仍独立工作，不把同文重复等同于抽奖。原始 XML 不因显示去重而重写。

设置采用每个直播间 1～50 条/秒，默认 50。抖音在有界采集线程中更新配额，无须重建健康连接；B 站下载核心与 XML 写入不改动，工作台按设置限制新增索引。改设置不停止录制或视频处理。旧索引按 2048 行批次让出事件循环，用现有 danmaku_filters 保存 length/repeat/rate 标记；查询先过滤再做范围、搜索和 LIMIT。删除素材时这些标记随原有弹幕记录清理。

画面预览和 ASS 成片字号统一缩为此前的三分之二。渲染缓存版本递增，旧字号缓存不会复用到新导出；原分辨率、60 帧与 CQ/CRF 20 保持。既有成片不会重写。
