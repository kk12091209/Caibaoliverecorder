# 零预处理导出与预处理接手验证（2026-10-24）

本轮只在本地开发、测试，没有提交、推送、打包发布或部署。基线是本轮开始时的完整工作副本，包含此前未发布的原画面复制、音轨复用及精确缓存剪辑；不是线上版本或 Git HEAD。

## 实现与保留条件

- 视频回读与弹幕寿命分开：ASS 继续使用全局排版，视频根据已知 B 帧重排和帧率保留必要解码前滚，再回到关键帧。旧元数据不完整时继续回读六秒。没有删减弹幕、字号、分辨率、帧率或编码质量参数。
- 连续处理最多两块、合计最多 120 秒，同一已封口来源且编码头一致才启用。按累计帧数强制关键帧、分段并重置时间戳，每块核对帧数、起点、时长、编码签名。分段语义参照 [FFmpeg 官方文档](https://ffmpeg.org/ffmpeg-formats.html#segment)，实际不兼容时只回退相应区间；后台仍使用各自的来源验证、空间预留、缓存发布和租约。录中处理、资源保护、动态连麦头像及不适合合批的区间沿用单块路径。
- 硬件前台合批在首轮 ABBA 中反而慢 2.82%（53.604 → 55.116 秒），因此未保留为默认策略。最终候选的硬件前台保持原有独立、最多两路分块；后台和适合的软件缓存路径可连续处理。首轮的性能证据与候选保留在 `benchmark/`、`after-accepted/`，不能把这份结果当作最终版本提速。
- 中间视频块由本地处理进程读取，省去每块将 MP4 文件头搬到文件前面的额外数据搬移。最终两个用户 MP4 继续执行 `+faststart`。测试同时检查了中间块与最终 MP4 的 box 顺序。
- 导出可接用当前正在处理且签名一致的批次，入队即可返回。已结束、来源封口、请求覆盖当前批次才接用；很短的剪辑不等待无关的整块完成。没有有效缓存的大型 CPU 冷导出保留原来的整来源处理路径，避免因等待第一块而改走较低预算的缓存处理。取消、样式/来源失效、录制开始、用户暂停和关闭仍会中断相应工作；最后一个导出消费者离开时释放等待关系。

## 方法

Apple M5、10 核、16 GiB，Node 24.12.0、FFmpeg 9.0.2、VideoToolbox 与固定 Noto Sans CJK SC 字体。动态 `testsrc2` 1080p30 H.264/AAC 原片，取 120 秒作为两个来源，中间五秒真实断流，共约四分钟有效画面，每秒三条中文弹幕，弹幕输出 1080p60。

正式零缓存用例在任何 `prepareNext()` 之前运行。先断言没有可命中的视频缓存、没有预处理计划，再计时 `enqueue()` 至两份完整 MP4 发布完成，包含硬件可用性探测、元数据、绘制/编码、原画面封装、音轨复用、最终封装和保存。随后核对输出，并再次确认冷导出没有建立后台视频缓存。测量直接覆盖用户发起导出的处理，不用“后台准备＋已准备导出”的相加结果代替。

预处理阶段另在无视频缓存的条件下计时；此时同素材的元数据和字体已被前面的冷导出读取，是一个相同顺序的对照，不能当作进程初次启动的全部成本。源文件创建、导入与输出验证不计时。按旧→新→新→旧串行运行，各版两次，没有同时运行回归套件或主动清空系统文件缓存。零视频缓存不等于清空了操作系统文件缓存。

四分钟样本线性外推两/三小时，包括启动、探测等固定开销；不是两/三小时实录或长时间处理实测。设备负载、编码器、弹幕密度、缓存容量、磁盘和散热都会影响实际等待。

预处理与已准备保存的长时估算还假设缓存空间足够；达到空间上限时只保留可安全完成的部分，不能保证两／三小时素材都已准备好。完全无预处理的双文件导出估算不依赖已有视频缓存。

## 正确性检查

缩短回读在 B 帧设置分别为 0 / 2 / 8 的短源上与保留六秒回读的参考逐帧摘要一致，包含非零全局起点和精确切点。连续处理覆盖 30 / 60 fps、非自然 GOP 边界的强制关键帧、独立解码和原质量编码对照。相关测试还覆盖复制/连续处理失败回退、真实子进程取消、空间不足、缓存与来源读取租约释放、同配置导出接手、样式变化拒绝接手、短剪辑不等待长批次，以及新录制抢占。

性能对照逐份核对 H.264、1920×1080、纯净版 30 fps / 弹幕版 60 fps、音画时长、首尾与分块/重连附近解码；双文件 AAC 音轨摘要一致。前后版本在相同时间点比较缩小灰度帧，属于抽样验证，不等于四分钟全分辨率逐帧全量比对。

## 复现

从 `live-editor` 执行，FFmpeg、FFprobe、字体可通过对应参数指定：

```sh
node scripts/benchmark-export.mjs \
  --suite cold \
  --before /absolute/path/to/this-round-before \
  --after /absolute/path/to/frozen-candidate \
  --source /absolute/path/to/source-1080p.flv \
  --seconds 120 --sources 2 \
  --output /absolute/path/to/new-result-directory
```

本地证据根目录：`/private/tmp/caibao-cold-export-20261024/`。`baseline-state.json` 记录开始时的分支、HEAD 和未提交状态；`before/` 保留基线，`after-final/` 是最终性能对照的冻结绘制候选，`benchmark-final/` 保留各轮数据。测试、源码快照和性能素材只使用独立临时目录，没有打开用户的实际录制数据库。

性能测量后补充了短剪辑／CPU 冷导出接手限制，以及下文的取消修正，最终运行源码冻结在 `after-verified/`，摘要在 `verified-hashes.json`。`benchmark-code-verification.json` 和对应差异记录了这两份快照之间的变化：绘制、解码、编码、音轨与封装代码相同；冷导出基准没有后台预处理管理器，不经过接手分支。取消修正不改变成功处理的媒体参数。不能把性能候选的整份源码摘要说成最终源码摘要。


## 最终结果

| 场景 | 修改前两轮 | 最终候选两轮 | 两轮均值变化 |
| --- | ---: | ---: | ---: |
| 零视频缓存，点击导出至两份 MP4 保存完成 | 54.840 / 56.098 秒 | 56.273 / 54.938 秒 | 55.469 → 55.606 秒，增加 0.25%，无可确认提速 |
| 无视频缓存的预处理 | 54.965 / 55.851 秒 | 53.261 / 54.121 秒 | 55.408 → 53.691 秒，减少 3.10% |
| 预处理完成后的双文件保存（对照） | 3.513 / 4.082 秒 | 3.594 / 3.582 秒 | 3.797 → 3.588 秒 |
| 预处理＋已准备双文件的相加值（另一流程） | 58.477 / 59.933 秒 | 56.855 / 57.704 秒 | 59.205 → 57.280 秒，减少 3.25% |

零缓存前后差 0.137 秒，且两版每轮范围重叠，不能说冷导出已经更快。绘制/编码仍占绝大部分工作；本轮没有进一步分离这两个阶段，因此不把它归因于某个硬件单元的极限。预处理阶段有小幅、两轮一致的改善，但样本只有两次，不能作为所有设备固定快 3% 的承诺。已准备保存阶段没有新增编码，不将其中约 0.21 秒的波动单独归为这轮的稳定收益。

任务实际仍完整绘制约 239.983 秒、复用视频 0 秒；纯净版和音轨直接复制，没有音频重编码，硬件没有软件回退。硬件前台保持四个独立绘制区间。按传入关键帧、目标起点及帧数计算的视频读取窗口合计由 255.890 → 243.890 秒，少 12 秒、约 4.69%；这是减少的来源读取/解码范围，不等于墙钟等待减少 12 秒。后台连续处理本身已由真实软件 FFmpeg 用例验证，是否在具体轮次启用仍由资源和计划条件决定，不假定后台每轮都合批。

弹幕版在所有对照时间点的缩小灰度抽帧摘要一致（最大 MAE 0），两份输出的帧率、音轨、时长、首尾与分块/重连附近解码通过，双文件 AAC 摘要相同。这里仍是抽样，不宣称四分钟全分辨率逐帧相同。

### 两小时与三小时估算

按 239.976 秒有效素材、同样的 1080p30 输入 / 1080p60 弹幕输出和本机两轮均值外推：

| 路径 | 两小时：修改前 → 修改后 | 三小时：修改前 → 修改后 |
| --- | ---: | ---: |
| 完全无预处理，直接取得两份完整成片 | 约 27 分 44 秒 → 27 分 48 秒 | 约 41 分 36 秒 → 41 分 43 秒 |
| 预处理本身 | 约 27 分 42 秒 → 26 分 51 秒，少约 51 秒 | 约 41 分 34 秒 → 40 分 16 秒，少约 77 秒 |
| 先预处理、再保存双文件的相加值 | 约 29 分 36 秒 → 28 分 39 秒 | 约 44 分 24 秒 → 42 分 58 秒 |

完全零预处理的用户等待可简化理解为本机约 28 / 42 分钟，**这轮没有证据证明能明显缩短**。这些秒级差值只是线性计算，不是长录像的实际测量精度。若录制中或闲时已经完成部分块，导出可以接手并复用它们；此收益取决于已完成量、当前批次进度和资源状况，没有用它替代本节零缓存结果，也没有把后台提前工作说成计算吞吐变快。

## 取消与并发收尾验证

完整回归和压力测试暴露了取消时的输入管道等待问题：子进程已经退出，来源读取租约也已释放，但带背压的输入在销毁前已经读到结尾，Node 管道仍等待一个不会再发出的 `end` 事件，造成调度名额和缓存构建迟迟不能结束。只销毁 stdin 仍不足以解决；取消时需要同时给可读输入标记明确的 AbortError、关闭 stdin，并继续等待管道、异步来源清理与子进程全部结束，不能用提前返回掩盖未释放的工作。

新增背压回归用例通过临时模块加载器还原旧的无错误销毁行为，稳定在 3 秒超时；相同用例在修正后通过，另有 stdin 正在 flush 的取消测试。模块加载器只保存在临时证据目录，不修改工作副本、不进入产品运行路径。真实 FFmpeg 的连续分块失败回退＋取消用例以 4 路并发运行 16 轮，全部通过，检查子进程、构建、空间预留和来源读取租约均归零。证据分别在 `cancel-regression-before.log`、`cancel-error-fixed.json` 与对应各轮日志。此前失败的压力日志保留用于追溯，不作为最终通过结果。

最终完整回归使用实际 FFmpeg／FFprobe 和固定字体，以 `node --test --test-concurrency=4 test/*.test.js` 执行，889 项中通过 885、跳过 4、失败 0、取消 0，耗时约 110 秒。跳过项为 Windows 路径大小写用例、两项真实录制核心启动／恢复用例和源码发布包验证；本轮不能因此宣称验证过 Windows 实机、真实平台长录或发行包。日志为 `full-verified.log`。`npm run build` 通过，日志为 `build-verified.log`；这只是本地前端构建，没有制作或发布安装包。
