# 弹幕处理优化与本地验证（2026-10-24）

本轮只修改本地开发版，不发布安装包或网站。对照基线是本轮修改之前的完整工作副本，包含此前录中提前处理和闲时调度优化，不是旧的 Git HEAD。

## 已落地的变化

- **避免重复排版**：顺序追加弹幕时只读取新行，沿用活动轨道、同秒条数配额和进场间隔。最多缓存两份完整布局；旧布局保持不可变。服务端已排序的字符串 ID 输入省去一次重复排序和整批对象复制。
- **保留已画完、尚待核对的片段**：索引暂时落后时，完整 MP4 进入独立的待验证区。索引追上后重新核对同一份来源和渲染签名，通过即可发布，无需再次解码、绘字和编码。未验证文件不能成为缓存命中，也不能导出。
- **正确性回退**：迟到弹幕、历史修改/删除/替换、过滤规则回撤、其他数据库连接写入、字体或样式变化均保守重建；渲染内容真的变化仍重新生成。没有修改字号、条数限制、区域、轨道规则、视频尺寸、帧率或编码质量参数。
- **资源约束**：待验证区最多 2 个结果、合计 256 MiB、120 秒绝对期限，不因反复验证而延长，不持有编码进程；磁盘预留仍计入总缓存预算。超额不保留。暂停、关闭、取消及退出清理自有结果；崩溃恢复只清理身份能确认且生产进程已退出的待验证文件。异常身份的文件不复用、不扩大删除范围。

没有新增运行时依赖、持久数据库表或用户操作步骤。浏览器预览的已有文字图片缓存保持原样。本轮没有改造 libass 字形绘制器或加入 GPU 合成。

## 排版对照

Apple M5、10 核、16 GiB、Node 24.12.0。隔离数据库模拟两小时、每秒 3 条、共 21,600 条不重复的普通弹幕，每分钟追加一次并生成完整布局，共 120 次检查点。保留真实聊天规则索引；没有迟到、回撤或改样式。按旧、新、新、旧顺序分别运行独立进程，取各两次均值。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 累计排版及规则准备耗时 | 4.433 秒 | 0.168 秒 |
| 布局读取总行数 | 1,306,800 | 21,600 |
| 各轮最慢一次布局 | 80.1～83.9 毫秒 | 3.4～3.7 毫秒 |
| 累计写入耗时 | 100.2 毫秒 | 175.3 毫秒 |

顺序追加场景的累计布局耗时减少 **96.2%**，约为原来的 1/26；新增插入防护触发器使这 21,600 次写入累计增加约 75 毫秒。将写入和排版合计，模拟两小时总计节省约 4.19 秒。所有 480 个检查点逐项比较弹幕 ID、时间、文字、颜色、轨道、坐标、宽度、入场延迟、速度和结束时间，完全一致。

这不是两小时视频导出提速 26 倍。收益集中在避免反复读取和排列历史弹幕；一次性打开完整历史素材仍需建立初始布局。当前对过滤表修改采用保守失效，新消息被判定为长文本等情况也可能触发完整重建，实际收益依流量与编辑操作而变。

## 绘制与编码的分项对照

使用同一份动态 `testsrc2` 1080p30 H.264/AAC 输入，取前 60 秒，统一输出 1080p60、3,600 帧、H.264 VideoToolbox、`-allow_sw 0 -q:v 65`、两线程及既有预处理编码参数。使用同一份 Noto Sans CJK SC 字体；无声音的视频缓存与正式预处理一致。先预热，随后按无 ASS、空 ASS、普通、密集及反向顺序各测两次，以下为均值。

| 场景 | 完整解码/滤镜/编码耗时 | ASS 滤镜区间累计耗时 |
| --- | ---: | ---: |
| 无 ASS | 12.662 秒 | 0.003 秒 |
| 空 ASS | 12.679 秒 | 0.934 秒 |
| 普通，每秒 3 条 | 12.656 秒 | 3.531 秒 |
| 密集，每秒 30 条 | 24.509 秒 | 24.072 秒 |

通过 FFmpeg `bench=start/stop` 包住 ASS 滤镜，在每帧记录滤镜区间耗时；这是区间墙钟时间，不是进程 CPU 用时，也不能与整条处理链耗时简单相减或相加。管道的解码、滤镜和硬件编码会重叠。普通场景的总时间与无 ASS 接近，微小正负差异属于波动；密集场景的主要瓶颈确实在绘字和叠加。帧率转换会多请求一个边界帧，计时约 3,601 次，成片均核对为 3,600 帧。

这是分项诊断，不是旧/新字形绘制器对比；当前绘制器没有替换。它支持把未来 GPU 合成实验集中到密集场景，但不证明换 GPU 后的实际收益。后续仍须验证字体/描边、透明度与颜色、上传下载成本、跨块边界和各平台回退。

## 片段等待核对的对照

使用真实的 60 秒普通弹幕编码，在第一次编码后确定性地注入一次“索引未就绪”。旧缓存丢弃后重新编码，新缓存等待后重新验证。两边都使用相同的当前绘制参数，以隔离缓存策略的影响。统计处理工作，不加入调度器的 10 秒重试等待。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 完整绘制次数 | 2 次 | 1 次 |
| 生成、验证及缓存发布耗时 | 25.879 秒 | 12.924 秒 |

该次等待用例耗时减少 **50.1%**。两份成片均为 3,600 帧；第 60、1,799、3,599 帧解码后的像素摘要一致。缓存单元测试另核对了保留文件和发布文件的完整字节一致。仅做一组真实编码重试对照，不能当成跨设备统计结果。

此用例证明暂时验证失败时能够省掉一次完整重绘，不代表真实直播每个块都能加速一半。真正的内容变化、保留超时或超出容量仍需重新处理；密集测试视频的单块约 478 MiB，超过待验证区限制，不会被无限保留。

## 复现和验证范围

```sh
node scripts/benchmark-danmaku.mjs \
  --before /absolute/path/to/pre-change/live-editor \
  --source /absolute/path/to/source-1080p.flv \
  --font /absolute/path/to/NotoSansCJKsc-Regular.otf \
  --ffmpeg /absolute/path/to/ffmpeg \
  --ffprobe /absolute/path/to/ffprobe \
  --output /absolute/path/to/new-result-directory
```

脚本不复用已有输出目录，不接触应用数据，不修改来源视频。输出 `report.json`、分帧滤镜日志及重试用的隔离缓存。基线须包含此前开发改动以及这轮开始时的 `server`、`shared` 和 `package.json`。非 macOS 使用固定两线程软件编码，不能把不同编码器或不同设备的数据直接比较。本机使用 FFmpeg 9.0.2；本轮没有 Windows 实机性能数据。

验证覆盖正常追加、同秒配额、三种密集布局及区域、迟到及同时间 ID 前插、文字和颜色修改、替换与删除、重复过滤回撤、外部 SQLite 写入、异步中途修改、取消和旧布局不可变；缓存覆盖超时、容量、并发等待、文件身份变化、暂停/禁用/退出、进程中断及恢复、从录中转为录后。黄金布局摘要来自修改前实现，而非由新实现生成。

最终全量回归 **842 项：838 通过，0 失败，4 项按环境条件跳过**；跳过的是 Windows 路径专属用例、两项未配置的真实录制核心集成用例、源代码包环境用例。新增等待区和增量布局测试均实际运行。前端生产构建通过，`git diff --check` 通过。最终签名校验还覆盖了核对期间改历史文字必须拒绝发布、仅过滤未来弹幕不误伤已完成历史块。

原始本地结果目录为 `caibao-danmaku-20261024/benchmark-complete`，保留机器信息、逐轮数值、480 份布局摘要、滤镜日志和抽帧摘要；首次试跑因 FFmpeg 默认合并重复日志而无法确认逐帧样本数，该次未作为绘制数据采用。脚本已使用 `repeat+info` 保留完整采样，最终测量正常完成。

## 后续：密集弹幕（2026-10-24，本地开发版）

本节基线是上述优化完成后的工作副本。改进共用排版及 Canvas 预览缓存；FFmpeg/libass 绘制器、编码画质参数和并发调度上限没有替换。所有验证使用独立测试数据。

### 排列与遮挡

由五点抽样的峰值估计改为计算整个共同显示期间的屏内交叠面积积分，加入既有水平间距，并在候选位置之间平衡整体遮挡及最严重的一对。短暂交叉不再与持续数秒遮挡具有相同权重。评分数组、冲突断点工作区复用，不建立逐对冲突对象。渲染版本升为 9，避免复用旧排版位置；增量检查点和迟到/过滤回撤重建机制继续使用。

4 个固定随机种子，各覆盖每秒 15/30/50 条、全屏/三分之一区域、均匀/整秒涌入，共 **48 组**，每组 24 秒。使用独立的屏内矩形仿真，在每对弹幕的共同显示期间采样 61 次，累计“重叠面积 × 持续时间”，不读取生产算法评分。所有组的该指标均下降 **6.97%～36.02%**。其中三个随机种子未用于选择评分方式。逐条核对 ID、文字、宽度、源时间、速度、进场延迟和结束时间，均相同。

这是保守文字矩形的估算指标，不是实际字形遮挡像素比例或主观可读性提升百分比；也不保证每一对、每一帧都改善。受面积和字数限制，极端密集时仍会重叠，未通过减条数、缩字号或额外延迟隐藏问题。更精确的积分会增加部分密集布局的算术工作，不能宣传为单次排版普遍更快；此前的增量排版及录中规模保护仍保留。

复现：

```sh
node scripts/benchmark-dense-danmaku.mjs \
  --before /absolute/path/to/previous/live-editor \
  --output /absolute/path/to/new-result.json
```

### 预览绘制

发现当同一屏文字图片总量超过 20 MiB 时，原先逐条 LRU 淘汰可能形成循环失效，每一帧重复生成全部图片。新策略保护本帧仍可见的缓存子集，只淘汰不再可见的项；超额部分复用一个临时 Canvas 绘制。常驻图片缓存仍为 20 MiB，额外临时 Canvas 不包含在这个计数内。完全移出画面的文字不再触发光栅化；透明度、速度、区域变化保留仍适用的文字图片，字体/字号/缩放变化继续失效。

本机 Chrome 隔离会话，1440×1000、DPR 2，1080p 测试视频，每秒 50 条独立文字，默认字号。使用真实 `DanmakuOverlay.vue`；基线组件使用相同的新排版，以隔离缓存策略的影响。按旧、新、新、旧运行，排除首次度量/字体准备的窗口，按实际绘制帧数加权：

| 指标 | 原缓存方式 | 优化后 |
| --- | ---: | ---: |
| 每帧 JS 绘制耗时 | 11.913 毫秒 | 3.217 毫秒 |
| 每统计窗口的绘制帧数均值（窗口约 1 秒） | 22.875 | 57.375 |
| 每帧重新光栅化的文字图片 | 300 | 199.71 |
| 稳态已缓存图片最大量 | 19.87 MiB | 19.87 MiB |

该场景单帧绘制耗时下降约 **73.0%**。统计的是 Chrome 中 Canvas 提交工作的墙钟时间，不是整个设备 CPU 或 GPU 用时；窗口长度和调度有波动，帧数不能解释为所有设备的帧率承诺。超额图片仍需重新绘字，未通过增加缓存预算掩盖工作集问题。4 次固定时间点的完整 Canvas 像素 SHA-256 均相同；另验证 5 次连续字号/透明度/区域/速度切换，原方式与新方式逐场景像素摘要一致。

验证页为临时的 `/dense-qa?qaMetrics=1`，只挂载真实弹幕组件及隔离视频，没有访问应用数据。Browser 插件未提供，使用现有 Playwright 和隔离 Chrome；桌面检查了页面身份、非空、无框架错误覆盖层、播放、跳转及区域按钮。首个基线页面的 favicon 404 属于测试外壳，未发现业务脚本错误。390×844 的独立手机尺寸会话验证区域按钮和像素边界；桌面直接缩小窗口的首次截图出现合成残留，已用新会话重测，不采用该截图作为证据。此处不代表 iPhone 实机验证或完整主界面验收。

### 视频导出与试验取舍

相同的 20 秒 1080p30 动态输入、每秒 30 条、输出 1080p60 / H.264 VideoToolbox `-q:v 65`，两线程，按旧、新、新、旧对照：旧布局平均 **7.961 秒**，新布局平均 **7.952 秒**，差异约 0.1%，视为无可确认的导出提速。每个成片均为 1,200 帧、1920×1080、YUV420P；修改前后编码质量参数相同。预览的 73% 收益不能套用到导出时间。

试验过在同一 FFmpeg 滤镜图中将画面分成两个高度区域、各自绘字后拼回。20 秒、1,200 帧的未压缩像素摘要逐帧一致，但耗时从 **7.686 秒增至 9.072 秒**，约慢 18%；未接入业务或添加额外工作进程。GPU 合成仍未接入。
