# 录制恢复机制（开发中）

此改动尚未发布，针对 B 站录制核心和编辑服务的监控链路。抖音录制的恢复逻辑沿用原实现。

## 检测与恢复

- 核心每 2 秒检查一次，使用单调计时，系统校时不改变超时判断。
- 默认连续 10 秒未收包，沿用核心网络超时设置，触发断开；仅有零星字节不能掩盖写入停滞。
- 首次连接给文件写入和有效媒体 20 秒宽限；开始写入后，文件停止写入、已出现的音频或视频时间不推进达到 15 秒，主动断开。只在实际写入完成后发布录制统计。
- 正常数据仍按关键帧分组；长 GOP 按约 4 秒媒体时间一批写入（另有 4096 标签上限），分批不创建新文件、不重编码。手动或定时分文件仍等待视频关键帧。避免长 GOP 积压在内存，被误判为写入卡住。
- 上游连接结束后继续排空已经收到的内容，保留写入守护；正常排空不按无网络数据误断开。
- 编辑服务观察到进度停滞约 8 秒后显示恢复状态；持续约 30 秒仍不推进时，按房间串行请求停止。后续状态查询确认旧任务不再录制，才请求启动。恢复动作最短间隔 30 秒，不终止共享核心，不影响其他房间。
- 用户停止、移除房间或退出优先。没有录制任务时不绕过核心的标题过滤、加密房间等策略；仅继续本监控发起的恢复。旧核心不提供进度统计时不凭空判断停滞。
- 收到新的有效输出推进后才确认恢复。仅有“正在录制”标志或计数归零，不作为成功依据。

上述时间是检测及发起恢复的阈值，不是保证恢复完成或漏录时长的上限。网络持续不可用、平台不返回直播流、磁盘写入无法结束时仍可能延迟；磁盘任务无法安全退出时显示等待，不并行启动第二个写入任务。

## 素材与日志

保留原来的录制时间坐标，不挤掉真实空档，避免改变选段和弹幕对应位置。只有前一源文件整理完成后才判断其后的空档，索引尚未完成不报告漏录。已确认的空档显示斜纹、缺失时长和可用片段时长；定位到空档沿用跳往下一片段的行为。部分波形无法读取会单独标注，不等同于确认漏录。

日志新增距收包、写入、音视频推进的间隔，以及恢复请求、确认恢复、文件媒体时长、打开至关闭时长和字节数。继续沿用脱敏和容量限制，不记录直播流地址、认证信息或弹幕正文。历史缺失内容无法补录。

## 验证与构建

新增核心测试覆盖网络中断、零星收包、时间戳冻结、写入停滞、排空、长 GOP 分批及关键帧分文件；编辑服务测试使用模拟单调时间和实际 `Recorder.poll()`，覆盖短暂抖动、40 分钟正常推进、确认停止、请求超时、重试间隔及用户停止。

```sh
dotnet test test/BililiveRecorder.Core.UnitTests/BililiveRecorder.Core.UnitTests.csproj --framework net8.0
cd live-editor
npm test
npm run build
```

macOS 回归需将 `TMPDIR` 指向真实路径（如 `/private/tmp`），并设置 `FFMPEG_PATH` / `FFPROBE_PATH` 为本机可执行文件；部分旧媒体测试默认查找 Windows 运行包路径。发布时重新编译 CLI 核心、编辑服务和页面，不复用旧的 `runtime/recorder` 二进制。
